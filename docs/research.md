# Функции для OSINT-расследований на данных из заметок

SplitHistory уже устроено как граф знаний с гео- и временной привязкой — это ровно та
структура, вокруг которой строятся инструменты link-analysis (Maltego, i2 Analyst's Notebook,
Gephi) и investigative-timeline-инструменты (Aleph, TimelineJS). Раздел 8 исходной идеи прямо
называет журналистов и аналитиков одной из целевых аудиторий («для историко-географических
расследований»). Этот документ — что именно можно добавить, чтобы приложение реально
поддерживало такую работу поверх **собственных заметок пользователя** (не живой скрапинг
внешних источников — это отдельный, гораздо более рискованный периметр, см. раздел
«Что сознательно не делаем»).

Все фичи ниже работают на данных, которые пользователь сам занёс в хранилище — то есть это
инструменты анализа *своих* исследовательских заметок, а не автоматического сбора данных о
людях из интернета. Это принципиальное ограничение задаёт как объём, так и этичность раздела.

## 1. Расширенный граф связей (link analysis)

**Что.** Сейчас граф — это либо весь 3D-вид (все слои сразу), либо 2D-вид одного слоя. Для
расследования нужен третий режим: граф **по всей базе, без разбивки на слои**, с фильтрами —
именно так работает Maltego/i2: не «слой Х», а «всё, что связано с этим узлом».

**Функции:**
- **Граф окрестности узла** — выбрал заметку → показать её и всех соседей на N шагов (1/2/3),
  независимо от того, на каком они слое. Технически: BFS по `note.links` от выбранной заметки,
  глубина настраивается ползунком. Переиспользует `computeGlobalLayout`/`computeLayerLayoutPixels`
  из `layout.js`/`layout2d.js`, только на отфильтрованном подмножестве узлов.
- **Кратчайший путь между двумя сущностями** — «как А связан с Б» — классический
  investigative-запрос («через какие посредники деньги/влияние/родство дошли от одного до
  другого»). Обычный BFS/Dijkstra по графу связей (веса рёбер = 1, если не вводить типизацию
  «силы» связи).
- **Метрики центральности** — degree (сколько связей) уже частично есть как «вес слоя»
  (`getLayerStats` в `store.js`); стоит вынести как отдельную метрику *на уровне заметки*, не
  только слоя — «эта личность упоминается в 12 заметках» сразу подсвечивает потенциально
  ключевые фигуры без чтения всего архива.
- **Фильтр по типу связи** — сейчас `link.type` — свободный текст («участвовал», «соперничал»,
  «упоминание» из авто-парсинга `[[ ]]`). Добавить возможность скрыть/показать граф только по
  конкретным типам отношений — «покажи только финансовые связи» / «только родственные».

**Реализация.** Новый режим в том же переключателе, что и 3D/2D («Граф» третьей кнопкой рядом с
`#view-mode-toggle`), рендер — переиспользование `layer2d.js`-подхода (canvas + свой layout), но
источник узлов — не `notesInLayer(layerId)`, а результат BFS/фильтра.

**Оценка.** L (BFS-режимы + UI фильтров), центральность на уровне заметки — S (чистая функция
поверх уже существующих данных).

## 2. Временной анализ (timeline correlation)

**Что.** Таймлайн сейчас — это только фильтр видимости. Для расследования важнее **находить
совпадения**, а не просто листать даты.

**Функции:**
- **«Что происходило одновременно»** — выбрал заметку с датой → подсветить все остальные
  заметки (в любом слое), чей диапазон пересекается с её диапазоном. Функция уже почти есть:
  `isNoteInTimeline` в `store.js` проверяет пересечение с `store.timeline`, нужно обобщить до
  пересечения диапазонов двух *заметок*, а не заметки и глобального выбора.
  Прямое применение — исторический алиби-анализ («мог ли этот человек участвовать в этом
  событии, если в это время он по другим заметкам был в другом месте»).
- **Плотность событий по времени** — гистограмма «сколько заметок на каждый год/десятилетие» —
  простая агрегация по `dateStart`, рисуется прямо над таймлайном (тонкая полоса из
  столбиков). Резкий всплеск — сигнал «тут что-то происходило», даже если исследователь этого
  не заметил при ручном просмотре.
- **Хронологический «плейбэк»** — автоматическое движение окна `[from, to]` по таймлайну с
  анимацией (`setTimeline` уже поддерживает произвольные `from/to`, нужен только таймер,
  сдвигающий их с фиксированным шагом) — наглядно показывает, как граф/карта «нарастают» во
  времени; полезно и для истории, и для восстановления хронологии событий в расследовании.

**Реализация.** Гистограмма и алиби-пересечение — чистые функции + небольшой рендер в
`timeline.js`. Плейбэк — `setInterval`, вызывающий `setTimeline` с нарастающим окном, кнопка
Play/Pause рядом с уже существующими кнопками масштаба.

**Оценка.** M (гистограмма + пересечения), S (плейбэк).

## 3. Геопространственный анализ

**Что.** Карта сейчас — фон для точек. Для расследований нужны операции *над* точками, не
только их отображение.

**Функции:**
- **Co-location — пересечение маршрутов/присутствия.** Если у двух сущностей есть точки/маршруты
  с датами, находящиеся в одном месте в одно время (после реализации `kind: 'route'` из
  `tools_ideas.md`) — это прямой сигнал «эти два человека/события пересекались физически».
  Функция: для каждой пары точек с датами — расстояние (haversine) < порога И даты в пределах
  окна (несколько дней) → «возможное пересечение».
- **Кластеризация по плотности** — на большой базе точки на карте сливаются; кластеризация
  (даже простая — сеточная, без библиотек) плюс подпись «14 заметок в этом районе» с
  раскрытием по клику. Полезно и для 2D-слоя (`layer2d.js`), и для мини-графа.
- **Расстояние/время в пути между событиями** — для проверки правдоподобия хронологии
  («событие А в Лондоне 1 марта, событие Б в Париже 2 марта с тем же действующим лицом —
  физически возможно ли успеть с учётом транспорта эпохи»). Минимальная версия — просто
  показывать расстояние по прямой между гео-точками двух связанных заметок с пересекающимся
  по времени контекстом; более точная версия (с учётом исторического транспорта) — не MVP.

**Реализация.** Всё — чистые геометрические функции (haversine уже фактически есть как
паттерн в `layout.js`/`worldMap.js` через проекции, нужно добавить именно метрику расстояния,
не только позиционирование). UI — всплывающая подсказка на карте при наведении на пару близких
точек, не отдельный экран.

**Оценка.** M (co-location + расстояния), S (кластеризация по сетке для отображения).

## 4. Оценка достоверности источников

**Что.** Прямое продолжение пункта «Источники и цитирование» из `tools_ideas.md` — но с фокусом
именно на верификацию, а не просто библиографию.

**Функции:**
- **Индикатор подтверждённости факта** — заметка, на которую ссылается ≥2 независимых
  source-заметки с разным `publisher`/`author` → зелёная метка «подтверждено»; 1 источник —
  жёлтая «частично»; 0 — красная «не подтверждено». Чистая функция поверх графа `links`,
  фильтрующая соседей по `type === 'source'`.
- **Обнаружение противоречий.** Если две source-заметки, ссылающиеся на одну и ту же
  event/person-заметку, сами по себе дают разные значения `dateStart`/`geo` для одного и того же
  факта (например, разные источники называют разные даты рождения) — подсветить конфликт.
  Технически: не автоматическое «понимание» текста, а структурное сравнение полей у заметок,
  которые оба ссылаются на один и тот же узел через `[[ ]]` — обнаруживает противоречия в
  *структурированных* полях (даты/гео), не в свободном тексте.
- **Журнал изменений как цепочка доказательств (chain of custody).** Из `tools_ideas.md` —
  «История изменений заметки»: для расследовательского контекста это не просто удобство отмены,
  а требование — кто и когда добавил факт, не менялась ли дата задним числом. Тот же механизм
  снапшотов, но с акцентом на неизменяемость лога (не давать пользователю редактировать сам
  журнал, только просматривать).

**Оценка.** M (индикатор подтверждённости — на существующей модели), M (противоречия по
структурным полям), переиспользует историю изменений из `tools_ideas.md`.

## 5. Экспорт в специализированные investigative-инструменты

**Что.** Не пытаться встроить в SplitHistory всё — экспортировать в инструменты, которые уже
умеют глубокий анализ.

**Функции (дополняют список экспорта из `tools_ideas.md`):**
- **GraphML/Gephi** — уже в основном бэклоге, для расследований это основной канал: серьёзный
  network-анализ (community detection, betweenness centrality) делает Gephi, не своё колесо.
- **KML/GeoJSON для Google Earth/QGIS** — та же логика для геочасти: свой рендер карты —
  для обзора внутри приложения, профессиональный гео-анализ — во внешнем ГИС-инструменте.
- **Отчёт-кейс (Markdown/PDF)** — экспорт подмножества заметок (текущий фильтр/выбранный слой)
  в связный документ с таймлайном, картой-скриншотом и списком источников — то, что реально
  прикладывается к публикации/делу. MVP — Markdown (просто конкатенация заметок в порядке дат
  + список ссылок), PDF — через существующий Electron `printToPDF` API окна, без новых
  зависимостей.

**Оценка.** Экспорт GraphML/GeoJSON — см. `tools_ideas.md` (M). Отчёт-кейс — M (Markdown),
S поверх него (PDF через встроенный Electron API).

## 6. «Кейс-файлы» — рабочие пространства расследования

**Что.** Расследование редко = всё хранилище целиком. Нужен способ сохранить конкретный срез:
набор фильтров (слои, диапазон дат, гео-область, поисковый запрос) + подборку заметок как
именованный «кейс», к которому можно вернуться.

**Реализация.**
- `case: { id, name, filters: { layers, dateFrom, dateTo, tags, searchQuery }, pinnedNoteIds,
  findings: string }` — сохраняется в `vault.json` рядом с `layers`/`notes` (или в отдельном
  `cases.json`, если планируется расшаривать кейсы отдельно от базы заметок).
- UI: панель «Кейсы» (аналог панели «Слои» — список, +, переключение), выбор кейса применяет его
  `filters` ко всему приложению (таймлайн, видимость слоёв, поиск) одним кликом.
- `findings` — свободное markdown-поле выводов расследования, отдельное от самих заметок-фактов
  (явное разделение «факт» vs «интерпретация факта» — важная практика в investigative-работе).

**Оценка.** M (модель + переключение фильтров), S (поле выводов).

## 7. Обогащение из внешних источников — WikiData/OSM

Уже упомянуто в исходной идее приложения и в `tools_ideas.md`. Для OSINT-контекста стоит
подчеркнуть отдельно: это единственный пункт во всём документе, где приложение обращается во
внешнюю сеть, — и именно поэтому он P2/P3, а не приоритет.

**Требования, если делать:**
- Запрос — только по явному действию пользователя на конкретной заметке («Подтянуть с
  WikiData»), никогда не фоново и не массово по всей базе без подтверждения.
- Явно показывать, какой запрос уйдёт (имя/название, которое ищем) и куда, до отправки.
- Результат — предложение полей для подтверждения, не автозапись поверх существующих данных.

**Оценка.** L (см. `tools_ideas.md`).

## Что сознательно не делаем (и почему)

Этот раздел так же важен, как список функций.

- **Никакого автоматического скрапинга соцсетей/сайтов по именам из заметок.** Это увело бы
  приложение из категории «личный исследовательский инструмент» в категорию «инструмент слежки
  за конкретными живыми людьми» — другой продукт, другие юридические и этические рамки
  (GDPR/152-ФЗ и аналоги, риск использования для преследования). Если пользователю нужны данные
  из внешних источников — он заносит их сам как заметку с указанием источника (см. раздел 4),
  осознанно и с атрибуцией.
- **Никакой деанонимизации/сопоставления с приватными базами данных.** Co-location и
  «расследование» в этом документе — про сущности и факты, которые пользователь уже
  задокументировал сам (исторические фигуры, публичные события), не про поиск личных данных
  живых частных лиц.
- **WikiData/OSM — только по явному запросу**, см. раздел 7.
- Приложение не хранит и не обрабатывает данные о том, ЗА кем ведётся расследование, кроме
  того, что сам пользователь явно вносит как заметки — то есть модель данных остаётся такой же
  «заметки + связи + гео + время», как и для истории/культурологии, без специального
  «профиля персоны для слежки». Это осознанное архитектурное ограничение, не пробел.
