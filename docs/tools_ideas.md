# Идеи инструментов для работы с заметками (история/география/контекст)

Рабочий бэклог для SplitHistory: что добавить, чтобы приложение было реально удобным
исследовательским инструментом, а не просто визуализацией графа. Список отсортирован по
приоритету (P0 — следующее, что стоит делать; P2 — обосновано, но не срочно). У каждого пункта:
зачем это нужно, как встраивается в текущую архитектуру, поэтапный план и как проверять.

Текущая архитектура, на которую всё это опирается: `src/store.js` (модель данных + pub/sub),
`src/scene.js` (3D), `src/ui/layer2d.js` (2D-граф слоя), `src/ui/noteWindows.js` (редактор заметки),
`src/ui/treePanel.js` (дерево/группировка), `data/vault.sample.json` (формат хранилища).

Тестирования в проекте пока нет вообще (ни одного `*.test.js`, ни раннера). Прежде чем строить
поверх этого много новой логики, стоит завести минимум — см. [П0. Тестовая база](#p0-тестовая-база)
первым пунктом, иначе каждый следующий инструмент будет проверяться только вручную скриншотами.

## P0. Тестовая база

**Зачем.** Сейчас единственный способ проверить регресс — вручную открыть приложение и
пощёлкать (см. историю разработки: скриншоты, ручные клики). Это не масштабируется, когда
инструментов станет 10+.

**Реализация.**
- `vitest` (быстрый, ESM из коробки, не требует конфигурации бандлера) как dev-зависимость.
- Юнит-тесты для чистых функций без DOM/Electron: `layout.js`, `layout2d.js`, `projection.js`,
  `utils.js` (`resolveWikiLinks`, `extractWikiLinkTitles`, `parseTagsInput`, `formatDateRange`),
  `store.js` (`isNoteInTimeline`, `getLayerStats`, `computeStructureKey`-подобная логика).
- Для UI-модулей (`noteWindows.js`, `treePanel.js`) — не юнит-тесты, а чек-лист ручного QA
  (см. ниже в каждом пункте) плюс, по возможности, `@testing-library/dom` поверх jsdom для
  проверки рендера без реального Electron-окна.
- В `package.json` — скрипт `"test": "vitest run"`, в README — раздел "Тестирование".

**План внедрения.**
1. Поставить `vitest`, написать 5–10 тестов на уже существующие чистые функции (быстрая победа,
   заодно ловит текущие баги).
2. Зафиксировать в `CONTRIBUTING.md`/README правило: новая чистая функция — новый тест.
3. Постепенно выносить логику из UI-модулей в чистые функции именно для тестируемости
   (например, `resolveLinkTargetForTitle`, `buildTreeGroups` уже частично чистые — вынести явно).

**Как проверять.** `npm test` в CI/локально; для ручных чек-листов — единый файл
`docs/manual_qa_checklist.md` (создать по мере роста списка), куда каждый пункт ниже добавляет
свою секцию.

**Оценка.** S (1 день на каркас + первые тесты).

## P0. Источники и цитирование

**Проблема.** Слой «Источник/ссылки» из идеи приложения не реализован. Сейчас никак не отличить
заметку-факт от заметки-источника, нет полей для библиографии — а это базовая потребность
историка/журналиста («на основании чего утверждается дата/факт»).

**Реализация.**
- Новый тип заметки `source` уже есть в `TYPE_LABELS` (`src/utils.js`), но без своих полей.
  Добавить в модель заметки необязательный блок `citation`: `{ author, publicationYear, url,
  publisher, reliability }` (аналог полей BibTeX/Zotero, минимальный набор).
  `reliability` — шкала 1–5 (можно взять NATO Admiralty Code A1–F6 как вдохновение, но упростить).
- В `noteWindows.js`: если `type === 'source'`, показывать доп.секцию полей цитирования под
  «Свойствами» (те же паттерны debounce+updateNote, что уже используются для остальных полей).
- Связь «заметка цитирует источник» — обычная `[[Ссылка]]` на заметку типа `source`; в панели
  «Связи» такие ссылки можно визуально выделять другим цветом чипа (`link-chip.source`).
- В `infoPanel.js`/мини-графе — индикатор «заметок без единого источника» (простая метрика по
  слою: сколько заметок не имеют ни одной ссылки на `type==='source'`).

**План внедрения.**
1. Модель данных + поля в окне заметки (без индикаторов) — MVP.
2. Визуальное выделение source-ссылок в чипах связей.
3. Метрика «непокрытые источником» заметки в `infoPanel.js`.
4. (P1, отдельно) импорт BibTeX/Zotero — см. ниже «Импорт/экспорт».

**Тестирование.** Юнит: сериализация/валидация `citation` (не даёт сохранить `reliability` вне
1–5). Ручной чек-лист: создать source-заметку → заполнить поля → сослаться на неё из
event-заметки через `[[ ]]` → убедиться, что чип связи выделен как «источник».

**Оценка.** M (2–3 дня).

## P0. Нечёткие даты и именованные периоды

**Проблема.** Сейчас `dateStart`/`dateEnd` — только точный год. Для истории норма — «ок. 1200
г.», «первая половина XIV века», «эпоха Возрождения» без точных границ. Это прямо из идеи
приложения («плавающее окно / периоды / эпохи»), но не реализовано.

**Реализация.**
- Расширить дату заметки: `dateStart`/`dateEnd` остаются числами (для сортировки и таймлайна),
  плюс необязательные `dateApprox: boolean` (рисовать «ок.») и `periodLabel: string`
  (произвольная подпись типа «Ренессанс» поверх диапазона).
- Отдельная сущность «именованный период» — по сути обычная заметка на новом системном слое
  `periods` (или просто `type: 'period'` в существующей модели) с `dateStart`/`dateEnd` и без
  гео; другие заметки могут на неё ссылаться через `[[Ренессанс]]`, что даёт «все заметки внутри
  периода» бесплатно через уже существующий граф связей.
- В `formatDateRange` (`utils.js`) — если есть `dateApprox`, добавлять «ок.» к выводу.
- В `timeline.js` — период как заметка рисуется на шкале отдельной горизонтальной «плашкой»
  (диапазон), а не точкой — небольшое расширение `renderTimeline`.

**План внедрения.**
1. `dateApprox` + `formatDateRange` — самое дешёвое, делать сразу.
2. Заметки-периоды без спец. отрисовки на таймлайне (пока просто обычные заметки).
3. Плашки периодов на шкале времени (отдельная итерация, нужен новый рендер-слой в
   `timeline.js` — полоса под тиками).

**Тестирование.** Юнит на `formatDateRange` с `dateApprox`. Ручной чек-лист: создать период
«Ренессанс» 1400–1600, сослаться на него из заметки о Галилее, проверить что период виден на
шкале как плашка, а не точка.

**Оценка.** S (dateApprox) + M (плашки на шкале).

## P1. Геометрия: регионы и маршруты вместо только точек

**Проблема.** Раздел 2 идеи приложения прямо требует «регион (границы ареала)» и «маршрут
(перемещения)», сейчас у заметки есть только `geo: {lat, lng}` — одна точка.

**Реализация.**
- Расширить `geo` до размеченного объединения: `{ kind: 'point', lat, lng }` (как сейчас,
  по умолчанию для обратной совместимости — заметки без `kind` трактуются как `point`),
  `{ kind: 'route', points: [{lat,lng,label?,date?}, ...] }`,
  `{ kind: 'region', ring: [[lat,lng], ...] }`.
- `projection.js`/`worldMap.js` уже умеют `latLngToPlane`/`lngLatToUnit` для точки — для
  маршрута/региона просто применить ту же проекцию к каждой точке контура и нарисовать
  `THREE.Line`/`ctx.lineTo` вместо одной сферы/точки (в `scene.js` и `layer2d.js`).
  Раскладка (`layout.js`/`layout2d.js`) для таких заметок не нужна — они и так «заякорены»
  геометрией, как сейчас работают point-заметки с `geo`.
- Редактор в `noteWindows.js`: для `kind: 'route'`/`'region'` — не два инпута lat/lng, а список
  точек с возможностью добавить/удалить (аналогично тому, как уже сделан список связей —
  переиспользовать паттерн `link-chip`/`links-list`).
- Маршрут с датами на точках (`date?` на каждой точке) — задел на будущий «плейбэк» (см. ниже).

**План внедрения.**
1. Расширить модель + обратную совместимость (`kind` по умолчанию `'point'`), ничего не ломая
   в существующих данных.
2. Отрисовка маршрута (полилиния) — самый частый кейс (перемещения человека, военная кампания).
3. Отрисовка региона (замкнутый контур/заливка) — исторические границы.
4. Редактор точек маршрута/региона в UI.

**Тестирование.** Юнит: миграция старых заметок (`geo: {lat,lng}` без `kind`) → трактуется как
point, ничего не падает. Ручной чек-лист: создать маршрут из 3 точек, проверить отрисовку в 3D
и в 2D-слое, убедиться что старые заметки с обычным `geo` по-прежнему рисуются точкой.

**Оценка.** L (4–6 дней, самая инвазивная модель данных из списка).

## P1. Полнотекстовый и комбинированный поиск

**Проблема.** Сейчас единственный способ найти заметку — прокрутить дерево слева. При 100+
заметках это не работает. Нет поиска по содержимому, только визуальная группировка.

**Реализация.**
- Поле поиска в шапке `#sidebar-left` (`index.html`, рядом с «группировать по»).
- MVP без индекса: раз данные целиком в памяти (`store.data.notes`), достаточно линейного
  фильтра по `title`/`content`/`tags` (для сотен заметок это доли миллисекунды, индекс не нужен
  раньше, чем заметок станет тысячи).
- Комбинированные фильтры (`query builder`): текст + диапазон дат (переиспользовать
  `isNoteInTimeline`) + слой + тип + теги — по сути пересечение уже существующих фильтров
  (`store.timeline`, `note.layerId`, `note.type`, `note.tags`) с текстовым.
- Результат поиска — подсветка/фильтрация дерева (`treePanel.js`) и одновременно фильтрация
  видимости в 3D/2D (переиспользовать уже существующий механизм `applyFilters`/`isNoteInTimeline`
  в `scene.js`, обобщив его до «видимость = таймлайн ∧ слой.visible ∧ поисковый фильтр»).

**План внедрения.**
1. Текстовый поиск по title/content, фильтрует только дерево слева (самое дешёвое, самое
   полезное).
2. Прокинуть тот же фильтр в `scene.js`/`layer2d.js` (заметки вне результата — тусклее/скрыты).
3. UI для комбинированных условий (дата+тип+тег) — отдельная панель "Фильтры", не только строка
   поиска.

**Тестирование.** Юнит на функцию `matchesQuery(note, query)`. Ручной чек-лист: ввести часть
слова из содержимого заметки → убедиться, что дерево и 3D-сцена синхронно фильтруются.

**Оценка.** S (текстовый поиск дерева) → M (прокидка в 3D/2D + комбинированные фильтры).

## P1. Импорт/экспорт данных

**Проблема.** Хранилище — изолированный JSON, из идеи приложения explicit-требование:
«Экспорт графов в Neo4j / Gephi», источники — WikiData/OpenStreetMap.

**Реализация (экспорт, самое дешёвое и безопасное — только чтение своих данных):**
- **GraphML/Gephi** — прямое отображение `store.data.notes`→ узлы, `note.links` → рёбра;
  чистая функция `exportToGraphML(data)` без DOM-зависимостей → легко тестируется юнитом.
- **GeoJSON** — все заметки с `geo` → `FeatureCollection` точек/линий/полигонов (пригодится
  после реализации регионов/маршрутов из пункта выше, но точки уже можно экспортировать сейчас).
- **CSV таймлайна** — для TimelineJS/внешней визуализации: `title, dateStart, dateEnd, layer,
  type`.
- Все экспортёры — чистые функции в `src/export/*.js`, дергаются из меню «Файл» в `main.js`
  (уже есть паттерн `dialog.showSaveDialog` для `vault:save-as`, экспорт добавляется тем же
  способом).

**Реализация (импорт — осторожнее, чужие данные):**
- **BibTeX/Zotero** → создаёт заметки `type: 'source'` с полями цитирования (см. пункт про
  источники) — парсер BibTeX, ~100 строк, без внешних зависимостей.
- **WikiData (SPARQL)** — по названию личности/события подтягивать даты рождения/смерти,
  координаты. Это уже сетевой запрос к внешнему сервису — требует явного согласия
  пользователя на каждый вызов (не делать автоматически/фоново), явной индикации в UI, что
  данные ушли на wikidata.org. Хорошая P2-фича, не первая в очереди из-за сетевой зависимости
  и необходимости продумать приватность (см. `docs/research.md`, раздел про внешние источники).

**План внедрения.**
1. Экспорт GraphML — самое востребованное (открыть граф в Gephi для серьёзного анализа связей,
   которого в самом приложении нет и не будет — не дублировать Gephi, а дополнять).
2. Экспорт GeoJSON/CSV.
3. Импорт BibTeX для источников.
4. (P2) Обогащение через WikiData по явному запросу пользователя на конкретной заметке
   («Подтянуть данные с WikiData» — кнопка, не автоматика).

**Тестирование.** Юнит на каждый экспортёр/парсер (вход — фикстура `vault.sample.json`, выход —
сравнение со снэпшотом). Ручной чек-лист: экспортировать текущее хранилище в GraphML, открыть в
Gephi, убедиться что все 13 заметок и связи на месте.

**Оценка.** M на экспорт (GraphML+GeoJSON+CSV вместе, они однотипные), M на BibTeX-импорт,
L на WikiData-интеграцию (сеть, ошибки, UX согласия).

## P1. Шаблоны заметок

**Проблема.** Каждая заметка заполняется с нуля. Для повторяющихся типов (личность/событие)
удобны заготовки полей — как Templater в Obsidian.

**Реализация.**
- `data/templates.json` (или внутри `vault.json` отдельным массивом `templates`) — набор
  `{ id, name, type, fields: {...}, contentTemplate }`, где `contentTemplate` — markdown с
  плейсхолдерами (`{{title}}`, `{{date}}`).
- В `createNoteWindow` (`src/ui/noteWindows.js`) — перед созданием пустой заметки показывать
  маленький выбор шаблона (или «Пустая заметка»), плейсхолдеры подставляются в `title`/`content`
  при создании.
- Пользовательские шаблоны редактируются в том же UI, что и слои (переиспользовать паттерн
  `layerModal.js` для модалки редактирования шаблона).

**План внедрения.**
1. 2–3 встроенных шаблона (Личность/Событие/Источник) без UI редактирования — просто константы.
2. UI создания/редактирования собственных шаблонов пользователем.

**Тестирование.** Ручной чек-лист: создать заметку по шаблону «Личность» → проверить, что
заголовок/тип/поля подставились корректно, плейсхолдеры не остались в тексте.

**Оценка.** S (встроенные шаблоны) → M (редактируемые пользователем).

## P2. Вложения и медиа

**Проблема.** Нет способа прикрепить скан документа, портрет, карту — то, с чем реально
работают историки.

**Реализация.**
- Файлы копируются в `<userData>/attachments/<noteId>/<filename>` через IPC-хендлер в `main.js`
  (аналогично уже существующему паттерну `vault:save`/`vault:open`, только `fs.copyFile`),
  в заметке хранится только относительный путь — не хранить бинарники в `vault.json`.
  Именно так уже спроектирована обработка world-карты как canvas-текстуры — то же разделение
  «данные отдельно от тяжёлых ресурсов».
- В `noteWindows.js` — секция «Вложения» под «Связями»: список миниатюр + drag-and-drop файла
  в окно заметки (`dragover`/`drop` на `.note-window-body`).
- Показ вложения — модальное превью (переиспользовать паттерн `.overlay` из `layerModal.js`).

**План внедрения.**
1. Прикрепление через диалог выбора файла (без drag-and-drop) — самое простое.
2. Drag-and-drop в окно заметки.
3. Превью изображений/PDF инлайн.

**Тестирование.** Ручной чек-лист: прикрепить jpg к заметке → закрыть/переоткрыть приложение →
убедиться, что файл и превью на месте (проверка, что путь не привязан к сессии).

**Оценка.** M.

## P2. Обнаружение похожих/дублирующихся сущностей

**Проблема.** При росте базы неизбежно заведут «Исаак Ньютон» и «И. Ньютон» как разные заметки.

**Реализация.**
- При создании заметки (`createNoteWindow`) или переименовании — простая эвристика похожести
  строк (Levenshtein/Jaro-Winkler, ~50 строк без зависимостей) по существующим `note.title`
  того же `type`; порог схожести → предупреждение «Похожая заметка уже существует: […]» со
  ссылкой открыть её вместо создания новой.
- Не блокировать создание — только предупреждать (историки специально заводят близкие, но
  разные сущности: отец/сын с одинаковым именем).

**План внедрения.**
1. Проверка только по точному совпадению после нормализации (регистр/пробелы) — ловит самые
   частые случайные дубли, почти без ложных срабатываний.
2. Fuzzy-похожесть с порогом — более полезно, но больше ложных срабатываний, нужно
   калибровать порог на реальных данных.

**Тестирование.** Юнит на функцию схожести с фикстурным набором пар «дубль/не дубль» и
ожидаемым результатом.

**Оценка.** S (точное совпадение) → M (fuzzy).

## P2. История изменений заметки (undo/version log)

**Проблема.** Автосохранение (уже реализовано) — это одновременно и удобство, и риск: нет
кнопки «отменить», случайная правка/удаление связи необратимы в рамках сессии без Ctrl+Z в
самом текстовом поле.

**Реализация.**
- Не полноценный git — локальный кольцевой буфер снапшотов заметки (последние N версий) в
  `note.history: [{ timestamp, snapshot }]`, пишется при каждом debounced-коммите содержимого
  (`updateNote` в `store.js` — один общий hook, откуда это писать).
- UI: в `noteWindows.js`, пункт контекстного меню «История изменений» → список версий → «Вернуть
  эту версию».

**План внедрения.**
1. Запись истории (без UI) — проверить, что не раздувает `vault.json` бесконтрольно (ограничить
   N версий и/или интервал между снапшотами, например не чаще раза в 5 минут).
2. UI просмотра и отката.

**Тестирование.** Юнит: после N+1 изменений в буфере остаётся ровно N версий (нет утечки
памяти/размера файла). Ручной чек-лист: изменить заметку 3 раза, откатить ко второй версии,
проверить содержимое.

**Оценка.** M.

## P2. Помощник связей (AI-подсказки, из раздела 8 исходной идеи)

**Проблема.** Явно упомянуто в исходном ТЗ как фича «на потом» — предложение связей на основе
совпадения дат/гео/текста.

**Реализация (без внешнего AI, эвристика, чтобы не тащить сетевую зависимость/API-ключи в
MVP):**
- Чистая функция `suggestLinks(note, allNotes)`: кандидаты — заметки с пересекающимся
  диапазоном дат (`isNoteInTimeline`-подобная проверка между двумя заметками) И близкой
  геолокацией (расстояние по haversine < порога) ИЛИ совпадением слов в `content` за вычетом
  стоп-слов.
- Показывается как ненавязчивая плашка в `noteWindows.js` под «Связями»: «Возможно, связано:
  […]» с кнопкой добавить `[[ ]]` в текст в один клик.
- Реальная LLM-интеграция (та, что упомянута в идее как «ИИ-подсказки») — отдельный P3, вне
  этого документа: требует продуманного UX согласия на отправку содержимого заметок во внешний
  API и конфигурации ключа пользователем.

**План внедрения.**
1. Эвристика по датам+гео (не требует NLP, самое дешёвое и достаточно точное для исторических
   данных, где совпадение времени/места — сильный сигнал).
2. + эвристика по тексту (менее точная, добавлять вторым слоем с явной пометкой «слабое
   совпадение»).

**Тестирование.** Юнит на `suggestLinks` с фикстурой (Ньютон/Лейбниц — должны предложиться друг
другу по пересечению дат и связи через Principia; случайная пара без пересечений — не
предлагается).

**Оценка.** M.
